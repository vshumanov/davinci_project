LANGCHAIN AND LANGGRAPH

WHAT IT IS

In October 2022 an engineer named Harrison Chase pushed a side project to GitHub. He was solving the same annoying problem over and over at work: wiring a language model up to external data and tools meant writing the same boilerplate every time. His fix was a Python library that turned that boilerplate into reusable pieces. He called it LangChain.

It grew fast. Fastest growing repository on GitHub within eight weeks. Thirty five million dollars raised within six months. Within a year it was the default starting point for building an LLM application, and it dragged an entire ecosystem of competing agent frameworks into existence behind it: LangGraph, CrewAI, AutoGen, LlamaIndex.

LangChain's original model was a chain of steps. Prompt goes in, model gets called, output gets parsed, maybe a tool runs, result comes out. Structurally that is a directed acyclic graph. It moves forward and it terminates. Fine for a lot of applications, and useless for anything that needs to loop, retry, wait on a human, or recover from a crash without losing its place.

LangGraph is the answer to that gap. It is a lower level orchestration framework, released later by the same company, that models an agent's execution as a graph instead of a pipeline. Nodes do work, edges decide what happens next, and a shared state object persists across the whole run. Crucially the graph can cycle. A node can hand control back to itself or to an earlier node as many times as the logic requires. That is the one structural feature a chain cannot express and an agent cannot function without.

As of late 2025, LangChain and LangGraph stopped being described as two competing tools and started being described as two layers of one stack. LangChain 1.0 and LangGraph 1.0 shipped together. LangChain is the agent framework: model integrations, a standard tool calling loop, a function called create_agent that gets you a working agent fast. LangGraph is the runtime underneath: durable execution, checkpointing, streaming, human in the loop. Since that release, LangChain's own agent loop runs on top of the LangGraph runtime. You are not choosing one over the other. You are choosing how far down the stack you need to reach.

A third piece worth knowing: LangSmith, the commercial observability layer. It traces what an agent actually did, evaluates outputs against test cases, manages prompts, handles deployment. LangChain and LangGraph are open source and free. LangSmith is where the company makes money.

WHY IT MATTERS

Strip the framing away and a language model is just a function. Text goes in, text comes out. No memory between calls, no ability to touch a file system or database, no concept of pausing for confirmation before doing something irreversible. Everything that turns a model into an actual application is glue code sitting around that function: memory, tools, retries, guardrails. Before LangChain, every team wrote that glue from scratch, slightly differently, mostly badly. LangChain standardized it.

That alone would matter, but the harder problem showed up once people moved from single shot completions to agents. An agent is not "call the model once and format the answer." An agent is "call the model, let it decide to use a tool, run the tool, feed the result back, let it decide again, maybe thirty times, maybe pause for human approval on a risky step, maybe run for six hours, and survive the server restarting at three in the morning." That last part is not hypothetical. Industry data on production agent failures puts the majority of incidents down to state management, not model quality. The model is usually fine. The bookkeeping around it is what breaks.

This is why LangGraph exists as its own product rather than a bolt on feature. Managing state for a long running, branching, occasionally paused process is a different engineering problem than composing prompts. It resembles workflow orchestration systems like Apache Beam or Google's older Pregel graph model more than it resembles a prompt templating library, and LangGraph borrows conceptually from both. Every step writes a checkpoint. If the process dies it resumes from the last checkpoint instead of from zero. If a step needs human sign off, the graph interrupts cleanly, waits, and resumes exactly where it stopped once approval arrives.

That durability is why companies with real uptime requirements, names like Klarna, Uber and J.P. Morgan get cited, adopted it for production agents instead of treating agents as a demo technology. An agent that can silently lose its state is a liability in any system touching money or customers. An agent built on a framework that treats state as a first class, checkpointed object is a different category of thing.

The other reason it matters is more mundane: it collapsed fragmentation. Model providers, vector databases, document loaders, tool integrations all used to need bespoke connective code per provider. LangChain's component model turned swapping one model provider for another, or one vector database for another, into a one line change instead of a rewrite. That standardization is unglamorous and is most of the real value.

THE CORE MECHANISM

LangGraph organizes everything around three primitives: state, nodes and edges.

The state is a shared object, typically a TypedDict, defined once when building the graph. It is the agent's working memory: the conversation so far, tool results, intermediate decisions. Every node can read it and return updates to it. Nothing is implicit. If information needs to survive from one step to the next, it lives in this object, in the open, not buried inside a framework internal nobody can inspect.

Nodes are plain functions. A node can call an LLM. A node can call an external API. A node can run deterministic Python with no model involved at all. That last point matters more than it sounds: most of the code in a real agent is ordinary control flow. The model gets invoked at specific decision points, not continuously. LangGraph is explicit about mixing hand coded, deterministic steps with LLM driven steps in the same graph, because most production logic should not be left to a model's judgment when a plain conditional would do the job more reliably.

Edges decide what happens after a node runs. A simple edge always goes to the same next node. A conditional edge inspects the state and routes to different nodes depending on what it finds, which is how branching gets expressed. Because edges can point backward to a node that already ran, the graph can cycle. This is the mechanism behind the classic reasoning and acting loop agents use: call a tool, look at the result, decide whether to call another tool or finish, repeat. In a plain linear pipeline that loop has to be faked with recursive calls or awkward retry wrappers. In a graph it is just an edge pointing at an earlier node.

After each step the state gets checkpointed to persistent storage. This is what makes an interrupt survivable. If a node is configured to pause, say to get human approval before an action proceeds, the graph stops cleanly at that checkpoint and waits indefinitely. When the human responds, execution resumes from that exact checkpoint with the full state intact, not from a rerun of everything before it. Recent optimization in the underlying storage engine, delta based checkpointing that writes only what changed instead of the entire state each time, has made this cheap even for long conversations with large state objects.

On top of all this, LangChain's create_agent gives a preconfigured version of that loop: a standard tool calling agent, provider agnostic across model vendors, customizable through a middleware system instead of by editing the loop itself. For a large share of use cases nobody touches the graph directly. You drop down to raw LangGraph only when you need control flow create_agent's defaults do not offer.

WHAT PEOPLE GET WRONG

The most common mistake: assuming LangChain is obsolete, a dead project replaced by LangGraph. It is not. It sits above LangGraph, not before it. Since the joint 1.0 release, LangChain's default agent runs on the LangGraph runtime under the hood. Building with LangChain does not mean avoiding LangGraph. It usually means using it without noticing.

The reverse mistake: reaching for LangGraph by default. If a task really is linear, call a model, parse a response, done, LangGraph's checkpointing and state machinery is overhead solving a problem that does not exist yet. A plain LangChain chain, or a direct model call, is the right tool. LangGraph earns its complexity cost only once there are loops, branches, long running steps, or a genuine need to pause for a human. Reaching for it out of habit produces systems that are harder to reason about for no operational benefit.

Third mistake: hearing the word graph and picturing a diagram, something to look at rather than something that runs. The graph is not documentation of the agent's logic. It is the agent's logic. The nodes and edges are the actual execution path, and the state object is the actual working memory of the running process, inspectable in real time. There is no separate real code underneath that the graph merely describes.

Fourth, more of a category error: treating an agent's value as being about autonomy, as if the framework's job is to get out of the model's way and let it improvise. In practice the value of these frameworks is almost entirely about constraining what the model is allowed to improvise. Deterministic steps, explicit state, conditional routing a human wrote, checkpoints a human can inspect: all of it exists to keep the unpredictable part, the model's own judgment, boxed into the smallest possible surface area. A well built agent is mostly scaffolding with a language model wired into a few specific junctions, not a model given the run of the place.

WHERE IT CONNECTS

Retrieval augmented generation, RAG, is the pattern LangChain is most credited with popularizing: instead of relying only on what a model memorized during training, you retrieve relevant documents from a database at query time and feed them into the prompt as context. The pattern predates LangChain, but LangChain's component model, a retriever plugged into a chain, made it the default architecture for grounding a model in a company's own data. In a modern LangGraph agent, retrieval is typically just one node the agent can call as a tool, invoked when the model decides it needs more context rather than injected on every turn regardless.

The Model Context Protocol, MCP, is the other connection worth knowing, since it is increasingly how tools reach an agent in the first place. MCP standardizes how a model gets access to external tools and data sources, the same way LangChain standardized access to model providers. An agent built on LangChain or LangGraph consumes tools exposed over MCP the same way it consumes any other tool, so the two ecosystems are complementary rather than competing. MCP standardizes the tool interface, LangGraph standardizes what the agent does with it once called.

Worth knowing the competitive landscape too. CrewAI positions itself around role based multi agent teams, several agents with defined personas collaborating, and markets itself as lighter and faster once the LangChain abstraction layer is stripped out entirely, with benchmark claims of several times the speed on simple tasks. Microsoft's AutoGen occupies similar territory from a different angle, conversation driven multi agent patterns. LlamaIndex leans harder into retrieval and data indexing than agent orchestration. None of these has displaced LangGraph in production deployments needing durability and fine grained control. The tradeoff each makes is trading some of that control and observability for simplicity or raw speed. Which one is right depends on whether the failure mode you are protecting against is a slow prototyping cycle or an agent silently losing its state during a six hour run.

Finally, LangSmith sits over the top of both, providing traces of what actually happened during a run, evaluation harnesses to test agent behavior against known cases before shipping changes, and the deployment platform most teams use once an agent needs to run somewhere other than a laptop. None of it is required, both frameworks work standalone, but it is the piece that turns "I built an agent" into "I can prove what my agent does and catch it when it stops doing that correctly."
